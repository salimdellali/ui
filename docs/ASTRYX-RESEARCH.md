# Astryx Research — Learnings for @salimdellali/ui

> Deep-dive into [facebook/astryx](https://github.com/facebook/astryx) (Meta's open-sourced design system, June 2026) compared against this library, with concrete recommendations.
> Researched 2026-07-07 from a clone of `facebook/astryx@main` (`@astryxdesign/core` v0.1.4, beta).

---

## 1. What Astryx is

- Meta's largest internal design system, grown over ~8 years, powering 13,000+ internal apps. Open-sourced June 2026 under MIT, currently in beta.
- **Stack:** React 19 + TypeScript + [StyleX](https://stylexjs.com) for styling, pnpm monorepo, Vitest + Testing Library, Storybook, changesets for releases.
- **Scale:** 150+ components, 10 theme presets, a CLI, an MCP server, page templates, and codemods.
- **Positioning:** "fully customizable and agent ready" — explicitly designed so humans *and* AI coding agents consume it the same way.

### Repo layout

```
packages/
  core/      # the component library (@astryxdesign/core)
  themes/    # theme presets, each its own package (butter, chocolate, matcha, y2k, ...)
  cli/       # astryx CLI: docs, component info, templates, swizzle, upgrade codemods
  charts/    # chart components
  build/     # build tooling
  lab/       # experimental components
apps/
  docsite/ storybook/ example-vite/ example-nextjs/ example-nextjs-tailwind/ ...
internal/    # dev utilities, vibe-tests (AI generation quality tests)
```

### Consumer story

Despite using StyleX internally, consumers need **no build plugin**: import a pre-built `astryx.css`, use typed React components. Works alongside Tailwind, CSS Modules, or plain CSS. This validates our pure-CSS approach — we're an even simpler version of the same story.

## 2. Their best practices, catalogued

### 2.1 Documented, enforced API conventions

They maintain a wiki page of API conventions every component follows:

| Convention | Rule |
|---|---|
| Booleans | `is*` for state (`isDisabled`, `isLoading`), `has*` for feature toggles (`hasClear`) |
| Callbacks | `on{Verb}` sync (`onChange`), `on{Verb}Action` async, `onOpenChange` unified for all overlays |
| Sizes | `'sm' \| 'md' \| 'lg'` everywhere, same pixel meanings everywhere |
| Direction | `start`/`end`, never `left`/`right` (RTL-safe) |
| Controlled | Controlled by default (`value` + `onChange`); uncontrolled via `default*` prefix (`defaultValue`, `defaultIsOpen`) |
| Boolean-or-config | `collapsible?: boolean \| {defaultIsCollapsed, onCollapsedChange, ...}` — `true` = defaults, object = configured |
| Slots | Passthrough elements: `icon={<Icon icon="check" />}` — parent never wraps or hoists child props |
| A11y-required props | `label: string` is **required** on interactive components; becomes visible text or `aria-label` when icon-only |
| Refs | React 19 ref-as-prop, no `forwardRef`; always set `displayName` |
| Naming | `Button`, not `AstryxButton` — no prefix on component names |
| Status | Shared shape `{type: 'error'\|'warning'\|'success', message?}` across form components |

### 2.2 `BaseProps` — a curated shared prop surface

Every component extends one `BaseProps<T>` interface: `React.HTMLAttributes` with ~50 footgun/obscure props explicitly `Omit`ted (`title`, `contentEditable`, `dangerouslySetInnerHTML`, RDFa, microdata, popover attrs…), plus:

- a typed `data-${string}` index signature (telemetry/testing hooks allowed by design),
- one styling escape hatch (`xstyle` in their case).

The API surface is deliberate instead of "whatever React allows".

### 2.3 A stable, prop-aware theming surface (their "no lock-in" secret)

Every component renders:

1. a **stable namespaced class**: `astryx-button`, `astryx-card` + variant classes (`secondary sm`),
2. **visual props reflected as data attributes**: `data-variant="secondary"`, `data-size="sm"`, `data-level="1"`.

Both are generated by one `themeProps()` util, and the `astryx` namespace itself lives in a single `naming.ts` module (source of truth for class prefix, data-attr namespace, CSS var namespace `--astryx-*`, and CSS layer names). Consumers/themes target `[data-variant]` selectors without touching internals; renaming the namespace is a one-line change.

### 2.4 Token architecture

- Tokens grouped by domain: color, spacing, size, radius, shadow, duration, ease, typography, type scale — with **semantic names** (`--color-text-primary`, `--radius-element`, `--size-element-md`).
- Dark mode via CSS **`light-dark()`**: theme tokens accept a string or a `[light, dark]` tuple compiled to `light-dark(a, b)` — no duplicated dark-theme blocks.
- `defineTheme({name, tokens})` creates a theme from a flat token map. Two modes: runtime `<style>` injection, or pre-compiled CSS + `data-astryx-theme="name"` attribute.
- Theme presets ship as **separate packages** (`@astryxdesign/theme-butter`…) so the core stays lean.
- Scale generators (`expandTypeScale`, `expandColorScale`, `expandRadiusScale`, `expandMotionScale`) derive full scales from a few inputs.

### 2.5 Colocated machine-readable docs (`*.doc.mjs`)

Each component directory contains `{Name}.doc.mjs` exporting a **typed `ComponentDoc` object** (typed via JSDoc against `docs-types.ts`):

```js
export const docs = {
  name: 'Button',
  category: 'Action',
  keywords: ['button', 'cta', 'submit', ...],
  usage: {
    description: '...',
    bestPractices: [
      {guidance: true,  description: 'Reserve primary for the single most important action…'},
      {guidance: false, description: 'Use a button for navigation — use a link instead.'},
    ],
    anatomy: [{name: 'Label', required: true, description: '...'}, ...],
  },
  props: [{name: 'label', type: 'string', required: true, description: '...'}, ...],
}
```

The CLI, docsite, and component playground import these directly — **no markdown parsing, one source of truth**, `guidance: true/false` encodes do/don't lists, `slotElements` tells the playground what to render in ReactNode slots.

### 2.6 File-header docs + `SYNC:` comments

Every source file starts with a structured header:

```ts
/**
 * @file Button.tsx
 * @input Uses React, ButtonHTMLAttributes, ReactNode
 * @output Exports Button component, ButtonProps, ButtonVariant types
 * @position Core implementation; consumed by index.ts, tested by Button.test.tsx
 *
 * SYNC: When modified, update these files to stay in sync:
 * - Button.doc.mjs (props table)
 * - Button.test.tsx (tests)
 * - Button.stories.tsx (storybook)
 */
```

A CI script (`check:sync`) plus the update protocol in CLAUDE.md keeps docs/tests/stories from drifting — cheap discipline, big payoff for agents and humans.

### 2.7 AI/agent readiness (their headline feature)

- **CLI as agent interface:** `astryx docs principles --dense`, `astryx component Button --dense`, `astryx template <name> --skeleton`, `astryx swizzle <Name>` (eject source), `astryx upgrade --apply` (codemods). `--dense` = token-efficient output for LLM context.
- **MCP server** so agents query the design system directly.
- **CLAUDE.md** contains a compressed capability matrix of what StyleX supports (so agents don't reinvent CSS features in JS) and a bootstrap ritual ("run these CLI commands at the start of every branch").
- **Vibe-tests:** an internal test suite that measures *how well LLMs generate correct component code* from their agent docs — including 10-turn degradation tests. They treat agent ergonomics as a tested, regression-guarded feature.
- Their stated principle: every change that made Astryx easier for AI made it easier for people.

### 2.8 Accessibility baked into APIs, not bolted on

- `label` required; icon-only mode reuses it as `aria-label`.
- Loading state announces via live region + `aria-busy`; `isDisabled` + tooltip uses `aria-disabled` (stays focusable) instead of native `disabled`.
- `prefers-reduced-motion` zeroes transition durations; hover styles guarded by `@media (hover: hover)`; focusable inputs keep `font-size ≥ 16px` on touch to prevent iOS zoom.
- Tests assert behavior through roles and accessible names (`getByRole('button', {name: 'Save'})`).

### 2.9 Testing & release engineering

- Colocated `*.test.tsx` per component (Vitest + Testing Library + user-event), behavior-focused.
- **Changesets** for versioning/changelogs; npm **trusted publishing** (provenance).
- Per-component **subpath exports** (`@astryxdesign/core/Button`) auto-generated by a `sync:exports` script with a CI check; `sideEffects` declared for CSS.
- CI: lint, tests, CLI smoke tests, codemod verification, preview deploys.

## 3. Us vs. them

| Area | Astryx | @salimdellali/ui | Verdict |
|---|---|---|---|
| Styling | StyleX → pre-built CSS for consumers | Pure CSS + CSS variables | ✅ Aligned — same consumer story, ours is simpler. Keep it. |
| Tokens | Primitives → semantic, domain-grouped | `--sd-*` primitives → semantic tokens | ✅ Aligned in structure |
| Dark mode | `light-dark()` tuples | `[data-theme="dark"]` override block | ⚠️ Theirs eliminates duplication (see rec. 3) |
| Namespacing | `astryx-*` classes, centralized in `naming.ts` | `sd-*` classes, convention only | ✅ Aligned; centralize when we add variants |
| API conventions | Written, enforced wiki page | None yet (only headings exist) | ❌ Gap — perfect timing to fix before interactive components |
| Prop surface | Curated `BaseProps` | Raw `HTMLAttributes<T>` | ⚠️ Fine for headings; revisit for interactive components |
| Variant reflection | `data-variant`/`data-size` attrs | N/A yet | 📝 Adopt when variants appear |
| Component docs | `*.doc.mjs` typed objects | Storybook stories only | ❌ Gap — great low-cost idea |
| Agent readiness | CLI + MCP + AGENTS.md + vibe-tests | Storybook MCP addon | ⚠️ We have a start; add an AGENTS.md |
| Tests | Colocated per component | Vitest configured, **zero component tests** | ❌ Gap |
| A11y | Baked into APIs + tested | Storybook a11y addon only | ⚠️ Adopt their API patterns for future atoms |
| RTL | Logical properties, `start`/`end` | Not considered yet | 📝 Free if adopted now |
| Releases | Changesets, monorepo, subpath exports | Single package, manual CHANGELOG | ✅ Fine at our scale |
| Themes | Preset packages | Single brand theme | ✅ Fine — we're a personal kit |

## 4. Recommendations

### Adopt now (cheap, high value, we're early)

1. **Write `CONVENTIONS.md`** before building the first interactive component. Steal their rules wholesale: `is*`/`has*` booleans, `on{Verb}` callbacks, `'sm'|'md'|'lg'`, `start`/`end`, required `label` on interactive components, controlled-by-default + `default*`, slots as passthrough elements, ref-as-prop. Retroactive API fixes are breaking changes — conventions now are free.
2. **Colocated tests per component** (`H1.test.tsx` etc.), asserting via roles/accessible names. The Vitest + Playwright browser setup already exists; it's unused.
3. **Dark theme via `light-dark()`**: instead of a `[data-theme="dark"]` block duplicating every semantic token, set `color-scheme: light dark` and define tokens once: `--bg: light-dark(var(--sd-paper), var(--sd-ink))`. Kills the duplication and directly addresses the existing tokens.css dark-refactor TODO (Baseline-supported since 2024).
4. **Use CSS logical properties from day one** (`margin-block`, `padding-inline`, `text-align: start`) — free RTL support, zero cost now, painful retrofit later.
5. **`prefers-reduced-motion` and `@media (hover: hover)` guards** as standing rules in component CSS.
6. **File headers + `SYNC:` comments** listing the files each component must keep in sync (`.tsx` / `.css` / `.stories.tsx` / `.test.tsx`). Add the update protocol to CLAUDE.md so agents follow it.

### Adopt soon (when the first variant-bearing component lands, e.g. Button)

7. **Reflect visual props as data attributes**: `sd-button` + `data-variant="primary"` + `data-size="md"`. Gives consumers (and Storybook/tests) a stable selector surface and costs a few lines.
8. **Centralize the `sd` namespace** in one `naming.ts` once more than one surface uses it (classes + data attrs + CSS vars).
9. **`*.doc.mjs` per component** — typed doc objects with `bestPractices` do/don't lists and anatomy. Even without a CLI, they feed Storybook autodocs, a future AGENTS.md, and the Storybook MCP addon.
10. **A curated `BaseProps`** shared type once interactive components exist — decide deliberately which HTML attributes pass through.
11. **`AGENTS.md`** at root: dense component list, token names, conventions, import patterns. We already ship the Storybook MCP addon; a static agent doc is the complementary half.

### Note for later / skip for now

- **CLI, templates, swizzle, codemods** — justified at 150 components, not at 3. Revisit if the kit grows past ~20 components.
- **Theme preset packages / `defineTheme()`** — single-brand personal kit doesn't need runtime theming. The `light-dark()` + semantic token structure keeps the door open.
- **Changesets / monorepo** — overkill for one package; current manual CHANGELOG is fine.
- **Per-component subpath exports** (`@salimdellali/ui/H1`) — nice for agents and tree-shaking guarantees; consider once the export count grows. If adopted, script the generation like their `sync:exports`.
- **Vibe-tests** — fascinating idea (regression-test how well LLMs use your library); file under "talk material", not backlog.

### npm-publishing insights spotted (for NPM-PUBLISHING.md)

- They declare `sideEffects` for CSS exactly like us — validation of our setup.
- `unpkg` / `jsdelivr` fields in package.json pointing to a UMD build for CDN playground use.
- npm **trusted publishing** (OIDC provenance from CI) instead of tokens.
- Auto-generated + CI-checked `exports` map (`sync:exports` / `sync:exports:check` scripts) — exports maps rot silently otherwise.
